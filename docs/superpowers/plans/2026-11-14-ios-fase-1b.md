# iOS Eerste lijn (fase 1b) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** In the app you scan a letter (several pages), the app recognises the text on the phone, uploads the scan in the background with progress and automatic retry (also when the app is closed or the server is unreachable for a while), shows the document with its processing status, and lets you review the server's proposals (each with its source) and confirm a task with a deadline.

**Architecture:** A new `BrievieScan` target (VisionKit scanner, Apple Vision OCR, JPEG encoding) and a new `FeatureDocuments` target (document list, scan flow, review screen). The upload queue lives in `BrievieCore/Upload`: every scan is written to disk as a ready-to-send `multipart/form-data` body before the upload starts, and is deleted only after the server answered 200/201. Uploads run on a background `URLSession` with the same CA pin as the rest of the app. Everything else goes through the `BrievieServer` seam and the generated client.

**Tech Stack:** As in 1a (Swift 6 strict concurrency, SwiftUI, iOS 18+, XcodeGen, swift-openapi-generator 1.12.2, Swift Testing, SwiftLint), plus VisionKit (`VNDocumentCameraViewController`), Vision (`RecognizeTextRequest`), ImageIO, PhotosUI, CryptoKit. No new package dependency.

**Spec:** `../Brievie_host/docs/SPEC.md` sections 10, 11 (`Brievie_ios`), 13, 14, 16 (step 1b and the acceptance criteria), 18, 19. Host plan: `../Brievie_host/docs/superpowers/plans/2026-11-14-host-fase-1b.md` (Tasks 1, 6 and 10 define the contract this plan uses). Previous plan: `docs/superpowers/plans/2026-11-13-ios-fundament.md`.

## Decisions taken with the owner (2026-11-14)

- Scanning happens in the app with the iOS document scanner; OCR runs on the phone and the text goes along with the upload. The server runs no OCR in 1b.
- The result is reviewed in the app (no web screens in 1b). AI on the server may be `off`: then the review screen is filled in by hand.

## Global Constraints

- Everything in the Global Constraints of the 1a plan still holds (English code, Dutch B1 je-vorm text only through the String Catalogs, Swift 6 strict concurrency with `async/await` only, no `!`/`try!`/`as!` outside tests, secrets only in the Keychain, dumb views, HTTPS only, VoiceOver and the largest Dynamic Type on every screen, `project.yml` is the source and the committed project must match, no dependency without a line in `docs/DECISIONS.md`).
- No API type written by hand: requests and responses use the generated types, also for the background upload (the metadata part is encoded from `Components.Schemas.UploadMetadataIn`).
- The queue survives everything (spec 19): a scan is complete on disk before its upload starts and is removed only after the server confirmed it (HTTP 200 or 201).
- Scan files on the phone: under Application Support, excluded from iCloud backup (`isExcludedFromBackup`), file protection `completeUntilFirstUserAuthentication` (the background upload must be able to read them while the phone is locked). No document image or text in a cache that outlives the process.
- No document content in logs (`Logger` with `privacy: .private` for anything but ids and codes).
- AI text is marked as AI text (spec 14, AI Act art. 50); a value with `needs_attention` is shown orange with a text label, not by colour alone.
- `BrievieAPI`, `BrievieCore` and the models in `BrievieScan` and `FeatureDocuments` compile for macOS so `make test` runs them; UIKit/VisionKit/PhotosUI parts behind `#if canImport(UIKit)`.
- Work on branch `feat/fase-1b`. Conventional commits. Do not push.

## Review Focus

1. The phone has no connection when the scan is made, and the app is closed afterwards: the upload starts by itself once the network is back and the document appears on the server (spec acceptance "Een scan zonder verbinding wordt later vanzelf geüpload, ook als de app gesloten is"). "Closed" means suspended or terminated by the system; when the **user** swipes the app away, iOS cancels its background uploads by design and they resume on the next launch (recorded in `DECISIONS.md`). → Task 5 (tests, including `test_scan_without_connection_is_uploaded_later`) and Task 9 (on the device).
2. The server answered but the answer got lost (connection dropped after the request was sent): the retry sends the same body with the same `client_id`, the server answers 200, the item leaves the queue; no duplicate document. → Tasks 4 and 5.
3. The server answers 401 while uploads are queued (device revoked): the app goes to pairing, the queued scans stay on disk and are uploaded after pairing again (or shown as failed when their workspace is gone); nothing is silently deleted, and a late 401 from an upload of the **old** pairing never wipes a new one. → Task 5.
4. The phone is low on storage or the scan has many pages: enqueueing fails with a clear Dutch message before anything is half-written; a body above the server limit (32 MiB, 30 pages) is refused in the app with a message, not after an upload. → Tasks 3 and 7.
5. OCR finds no text (a photo of a blank page, a handwritten note): the document is still uploaded with empty text per page, and the review screen works by hand. → Tasks 2 and 8.

### Task 4: Upload policy

Pure function; decides every next step of the queue.

**Files:**
- Create: `Sources/BrievieCore/Upload/UploadPolicy.swift`
- Test: `Tests/BrievieCoreTests/UploadPolicyTests.swift`

**Interfaces:**

```swift
public enum UploadOutcome: Equatable, Sendable {
    case status(Int, code: String?)      // HTTP answer; code from the error body when present
    case unreachable                     // no connection, timeout, DNS, connection lost after sending,
                                         // and every cancellation that was not our own trust refusal
    case untrusted                       // TLS refused by the pin (the delegate records this per task)
    case cancelledByUser                 // the app's own `delete`: no decision, the item is gone
}
public enum UploadDecision: Equatable, Sendable {
    case done                            // remove the item
    case retry(urlIndex: Int, after: Duration)
    case failed(code: String)            // keep the item, show it, user may retry or delete
    case revoked                         // keep the item, pause the queue, AppModel.sessionRevoked
}
public enum UploadPolicy {
    public static let backoff: [Duration] = [.seconds(30), .seconds(120), .seconds(600), .seconds(1800), .seconds(3600)]
    public static func decide(_ outcome: UploadOutcome, item: UploadItem, urlCount: Int) -> UploadDecision
}
```

- Rules: 200 and 201 → `.done`. `.unreachable` → next URL immediately (`after: .zero`) while `urlIndex + 1 < urlCount`, else back to URL 0 with `backoff[min(attempt, last)]` (a background task already waits for connectivity by itself, so this only happens when every URL was tried and failed with a real error). 429, 500, 502, 503, 504 → same URL with backoff. 401 → `.revoked`. 409 → `.failed("document_conflict")`. 404 → `.failed(code ?? "not_found")`. 411, 413, 415, 422 and other 4xx → `.failed(code ?? "http_<status>")`. `.untrusted` → `.failed("untrusted")` (a changed certificate is not fixed by waiting). Retries never end on their own: an upload waits as long as it takes.

- [ ] **Step 1: Failing tests:** one test per rule above, plus: a lost answer (`.unreachable` after sending) retries the same item (same id, same body; Review Focus 2); the backoff never exceeds 1 hour; the error `code` of a failed upload is kept only when it is in `ServerError.passThroughCodes` (plus `document_conflict`, `page_checksum_mismatch`, `workspace_not_found`), otherwise `http_<status>`.
- [ ] **Step 2:** Run; FAIL. Implement. Run; PASS.
- [ ] **Step 3:** Commit `feat(core): decide what happens after each upload attempt`.

```swift
public enum UploadEvent: Sendable {
    case sent(itemID: UUID, bytes: Int64, of: Int64)
    case finished(itemID: UUID, deviceID: UUID, outcome: UploadOutcome)
    case allEventsDelivered                       // urlSessionDidFinishEvents
}
public protocol UploadTransport: Sendable {
    /// Buffered (`.unbounded`) and created with the transport, so events of a relaunch are kept until the
    /// coordinator starts reading.
    var events: AsyncStream<UploadEvent> { get }
    func start(itemID: UUID, deviceID: UUID, url: URL, bodyFile: URL, boundary: String, token: String, earliestBegin: Date?) async
    func runningItemIDs() async -> Set<UUID>
    func cancel(itemID: UUID) async
}
/// Reads the pinned CA of the stored connection for every TLS challenge (Keychain, readable after first unlock).
public protocol UploadTrustProvider: Sendable {
    /// `nil` when nothing is stored or the Keychain cannot be read: the challenge is then refused.
    func currentTrust() -> ServerTrust?
}
public actor UploadCoordinator {
    public init(store: UploadQueueStore, transport: any UploadTransport,
                connection: @escaping @Sendable () throws -> (ServerConnection, String)?,
                onRevoked: @escaping @Sendable (_ deviceID: UUID) async -> Void,
                now: @escaping @Sendable () -> Date = Date.init)
    public func run() async                      // consumes transport.events; started once at launch
    public func enqueue(pages: [ScannedPage], workspaceID: UUID) async throws(UploadQueueError) -> UploadItem
    public func resume() async                   // start waiting items; `uploading` items the transport does not know -> start again
    public func retry(_ id: UUID) async          // failed -> waiting, attempt 0, urlIndex 0, then resume
    public func delete(_ id: UUID) async         // cancel + remove
    public func progressUpdates() -> AsyncStream<[UUID: Double]>   // a new stream per subscriber
    public func items() async -> [UploadItem]
    public func setEventsHandler(_ handler: @escaping @MainActor @Sendable () -> Void)  // AppDelegate's completion handler
}
```

- `BackgroundUploadTransport`: exactly **one** `URLSession` per process with identifier `nl.stijnvdpol.brievie.upload`, created at launch (also when the app is relaunched in the background). Its own configuration, **not** `SessionConfiguration.hardened` (whose 30 s resource timeout would kill slow uploads): `.background(withIdentifier:)`, `sessionSendsLaunchEvents = true`, `isDiscretionary = false`, `timeoutIntervalForResource` 7 days (the system waits for connectivity itself), no cookies, no credential storage, no cache; redirects refused. The delegate answers server-trust challenges with `UploadTrustProvider.currentTrust()`; `nil` → refuse (never fall back to system trust). It records per task that it refused trust, so that only that cancellation becomes `.untrusted`; every other `NSURLErrorCancelled` (user swiped the app away, system reasons) becomes `.unreachable`, and the transport's own `cancel` becomes `.cancelledByUser`.
- Request: `POST <url>/api/v1/workspaces/<workspaceID>/documents`, `Content-Type: multipart/form-data; boundary=…`, `Authorization: Bearer …`, `uploadTask(with:fromFile:)` (sets `Content-Length`), `taskDescription` = `"<itemID>/<deviceID>"`, `earliestBeginDate` only for a backoff after 429/5xx. The response's status and `{"code"}` (read from the task's received data) become an `UploadOutcome`.
- Coordinator rules: before any `await` that starts a transfer, the item is saved as `uploading` with the current `deviceID` (actor reentrancy cannot start it twice). `.revoked`: `onRevoked(deviceID of that task)` is called (`AppModel.sessionRevoked(deviceID:)` already ignores a stale device), running tasks are cancelled and their items set back to `waiting`; nothing is deleted. `allEventsDelivered` calls the stored handler on the main actor **after** the store is updated.
- `AppDelegate.application(_:handleEventsForBackgroundURLSession:completionHandler:)` passes the handler to `UploadCoordinator.setEventsHandler`.
- Navigation of responsibilities: `AppModel` does not know the coordinator; `RootView` calls `resume()` on `.ready` and on scene activation.
- `DECISIONS.md`: (1) the bearer token travels in a background task's request, which iOS keeps outside the app until the task ends (a short-lived upload token is later hardening); (2) a user swipe cancels background uploads by iOS design, they resume at the next launch; (3) one background session per process, trust read per challenge.

  - `test_scan_without_connection_is_uploaded_later` (spec acceptance): enqueue → `start` on URL 0; event `.finished(.unreachable)` on the last URL → `start` again with `earliestBegin` 30 s later; then `.finished(.status(201))` removes the item and its files (Review Focus 1);
  - with two URLs, `.unreachable` on URL 0 starts URL 1 at once;
  - a new coordinator on the same store, with the transport reporting the item as running, does not start it again on `resume()`; an `uploading` item the transport does not know is started again (killed while uploading);
  - calling `enqueue` and `resume` concurrently starts the item once;
  - `.finished(deviceID: A, .status(401))` calls `onRevoked(A)` once, cancels running tasks, keeps the items as `waiting`; `resume()` with a connection of device B starts them with `deviceID` B (Review Focus 3);

```swift
public struct ConfirmedReview: Equatable, Sendable { sender: String; documentType: String; letterDate: CalendarDate?; summary: String; summaryByAI: Bool; tasks: [TaskDraft] }
public struct ConfirmedTask: Equatable, Sendable, Identifiable { id: UUID; type: String; description: String; deadline: CalendarDate?; deadlineSource: String; deadlineQuote: String }
```

- Dates that are `date` in the contract (letter date, deadline) become `CalendarDate`, never `Date` (spec 19: "Een deadline is een datum, geen tijdstip"); views format them with a Gregorian calendar fixed to UTC so the day never moves.

- Error mapping as in 1a (`ServerError`); 409 `document_not_reviewable` and `document_not_failed` pass through as codes (`ServerError.passThroughCodes`).
