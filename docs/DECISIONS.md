# Decisions

One line per dependency or tooling choice, with the reason.

## Tooling

- **XcodeGen** — the Xcode project is generated from `project.yml`, so `*.xcodeproj` never causes merge conflicts.
- **SwiftLint** (`--strict`, `force_unwrapping` on) — the lint gate locally and in CI.
- **Swift Testing** — the test framework for all targets; ships with the toolchain, no package dependency.

## Package dependencies

Versions checked on 2026-11-13 against the GitHub tags; exact resolutions are in `Packages/BrievieKit/Package.resolved`.

- **swift-openapi-runtime** `from: 1.13.4` (newest) — runtime for the generated client; `BrievieCore` imports it only to unwrap `ClientError`.
- **swift-openapi-urlsession** `from: 1.4.0` (newest) — `URLSession` transport, so trust is decided by our own session delegate.
- **swift-http-types** `from: 1.8.0` (newest) — already a dependency of the OpenAPI packages; declared explicitly because `APIClient.swift` imports `HTTPTypes` for the bearer-token middleware.
- **swift-openapi-generator** `exact: 1.12.2` (newest is 1.14.4) — build plugin in `BrievieAPI` that generates types and client from `openapi.json` (`generate: [types, client]`, `accessModifier: public`, `namingStrategy: idiomatic`). Pinned below the newest release on purpose: from 1.13.0 the generator emits `public import` lines, and from 1.13.1 it also splits types into files that do not use all of them, which gives "public import ... was not used" warnings on Swift 6.3 (Xcode 26.4); upstream only silences them from Swift 6.4 (`@diagnose`, PR #947). 1.12.2 output compiles warning-free under Swift 6 with complete strict concurrency, so no setting is relaxed for `BrievieAPI`. Move to the newest release once the toolchain is Swift 6.4. Build-time only: nothing of the generator ships in the app.
- **Generator `filter`** — only the operations the app calls (`getHealth`, `getCaCertificate`, `pairDevice`, `revokeDevice`, `listWorkspaces`); a feature that needs another operation adds it to `openapi-generator-config.yaml`. This keeps the generated surface small and avoids generating schemas the app does not use.

## API client

- The contract's paths already include `/api/v1`, so the generated client's server URL is the plain server address from the QR code.
- `APIClient.make(baseURL:session:token:)` takes a `URLSession` rather than a `ServerTrust`: `ServerTrust` lives in `BrievieCore`, which depends on `BrievieAPI`, so `BrievieAPI` cannot name it. `LiveBrievieServer` (in `BrievieCore`) builds the pinned session, passes it in, and invalidates it after each call.
- `openapi.json` is a verbatim copy of the host's file (`make sync-api`), never edited by hand; `API_VERSION` holds its `info.version`.
- Phase 1b adds `listDocuments`, `getDocument`, `getDocumentPage`, `confirmDocument` and `retryDocumentProcessing` to the generator `filter`, plus the schema `UploadMetadataIn`: the JSON in the `metadata` field of the multipart upload, which goes through a background `URLSession` instead of the generated client. Nullable fields arrive as Swift optionals since the host writes them as type arrays (host decision 2026-11-14); a `date` stays a `String` in the generated types.
- `FlexibleDateTranscoder` reads timestamps with and without fractional seconds: the host (Pydantic) sends a fraction unless the time falls on a whole second, and the runtime's default transcoder accepts only the form without.
- Every session `LiveBrievieServer` uses refuses redirects (`PinnedSessionDelegate` and the one-off CA delegate): the API never redirects, and a followed redirect could carry the `Authorization` header or the pairing code to another host.
- Server error codes reach the app only from a closed set (`ServerError.passThroughCodes`, plus the codes mapped to their own cases); anything else becomes `http_<status>`. `ServerError.other` and `PairingError.failed` are diagnostic only and never shown to the user.


## Scanning (phase 1b)

- **VisionKit document scanner + Apple Vision text recognition, on the device** (owner decision 2026-11-14): the app is the only intake in 1b and the server runs no OCR. No new package dependency: VisionKit, Vision, ImageIO and PhotosUI ship with iOS.
- `VisionTextRecognizer` uses `RecognizeTextRequest` (accurate, language correction) with Dutch when the system lists a language with code `nl` (it does on macOS 26 / iOS 26: `nl-Latn-NL`), otherwise automatic detection. Lines are ordered top to bottom, then left to right.
- Pages are uploaded as JPEG, longest edge 2400 px, quality 0.7 (`PageImageEncoder`). Scanner pages and library photos are handed over as compressed data and decoded one at a time, already scaled down (ImageIO thumbnail with transform, which also applies the EXIF orientation), so a 30-page scan never sits in memory as full-size bitmaps.
- `PhotoImportButton` (PhotosPicker) is the way in where the scanner is unavailable (simulator, no camera).
- The test letter (`Tests/BrievieScanTests/Fixtures/letter-nl.png`) is drawn by `make-letter.swift` next to it.

## Upload queue (phase 1b)

- **One directory per queued document, not SwiftData.** `Application Support/Uploads/<id>/` holds `item.json` (the record) and `body.multipart` (the ready-to-send request body). The spec names SwiftData for the queue; a record next to its body is less code, the two disappear together, and a background upload needs the body as a file anyway. Reconsider for the document cache (1c).
- An item is written under `.incoming-<id>` and renamed when complete, so a crash never leaves half an item; leftovers are removed at start. A directory whose `item.json` is missing or not an item can never be uploaded: it is removed at start and the post list says once "1 scan kon niet worden gelezen en is verwijderd". A record that exists but cannot be opened yet (before the first unlock) is kept. The queue is excluded from backup and readable after the first unlock (the background upload reads it while the phone is locked).
- The item's id is the document's `client_id` on the server: a repeated upload finds the same document.
- Server limits are checked on the phone (`UploadLimits.server`: 30 pages, 32 MiB, 20000 Unicode code points of text per page, as the host counts them; longer text is cut between whole characters), so a scan that cannot succeed is never queued.

## Background upload (phase 1b)

- **One background `URLSession` per process** (`nl.stijnvdpol.brievie.upload`), created at launch, also when the system relaunches the app for finished uploads. Its own configuration instead of `SessionConfiguration.hardened`: that one's 30 s resource timeout would end every slow upload; here the system waits for a connection itself (up to 7 days per attempt). No cookies, no cache, no stored credentials, redirects refused.
- **Trust is read per TLS handshake** (`UploadTrustProvider`): the session outlives a pairing, so the pin comes from the stored connection each time. Without a readable pairing the connection is refused; there is no fallback to system trust for a pinned server.
- **The device token travels in the request of a background task**, which iOS keeps outside the app's process until the task ends. Accepted for now; a short-lived upload token is later hardening.
- **Swiping the app away cancels its background uploads** (iOS design). They stay in the queue and go out the next time the app opens. When the system itself ends the app, uploads continue. Such a cancellation counts as "unreachable", never as a failure; only our own refusal of the server's certificate is "untrusted".
- **Retry rules** live in `UploadPolicy` (pure): next URL at once, then back to the first with a backoff of 30 s up to 1 hour, forever; 401 pauses the queue and sends the user to pairing, nothing is deleted; other 4xx answers fail the item with a code from a closed set, and the user can retry or delete it.
- `AppModel` does not know the queue: `AppEnvironment.live` builds transport and coordinator, `RootView` calls `resume()` whenever the app becomes ready.

## Documents (phase 1b)

- **A second seam, `DocumentServer`**, next to `BrievieServer`: the document calls (`documents`, `document`, `pageImage`, `confirm`, `retryProcessing`) take a `DocumentScope` (address, trust, token, workspace). `LiveBrievieServer` implements both. Adding five methods to `BrievieServer` would have forced every pairing fake to grow with them.
- **`WorkspaceDocuments`** is what screens use: it tries the pairing's addresses in order, reads the token from the Keychain, and sorts every failure into a `DocumentsError` (revoked, unreachable, not verified, not found, conflict, ...).
- **`CalendarDate`** (year, month, day) for letter dates and deadlines, never `Date`: a deadline is a day, and a `Date` at midnight in Amsterdam is the day before in Los Angeles.
- A page image is read with a 20 MiB cap; `FakeDocumentServer` and `DocumentFixtures` live in `BrievieCore` because several test targets use them.

## Document list and scanning screens (phase 1b)

- `FeatureDocuments` holds the post of a workspace (`DocumentsModel`, `DocumentsView`) and the scan flow (`ScanFlowModel`). A workspace row opens it through a destination the app supplies (`WorkspacesView(destination:)`), so `FeatureWorkspace` does not depend on it. The tab bar of spec section 13 comes in 1c with the Today screen.
- Screens talk to the queue through the `UploadQueue` protocol (`UploadCoordinator` conforms); a scan on the phone and its document on the server (same id as `client_id`) are one row.
- The list refreshes every 3 seconds only while something is on its way (waiting, uploading, processing) and the screen is visible. There is no push in phase 1.
- All visible text of this target is in `DocumentStrings` (catalog key plus the Dutch default), also for views; the parity test keeps catalog and code equal. A viewer, or a role this app does not know, gets no scan button.

## Review screen (phase 1b)

- `ReviewModel` turns the server's proposals into a draft: a value the letter does not support (confidence 0) is shown as a hint, never pre-filled; a deadline the user changes becomes `manual` and loses its quote, so the source shown always belongs to the value; an invoice due date without a payment action adds a "Betaal de rekening" task. Nothing is sent before "Bevestigen".
- "Waar staat dit?" shows the letter text with the quote marked (`QuoteLocator`: ignores case, accents and line breaks; it only finds what to highlight). Marking the place on the page image needs text positions from Vision: later.
- AI-written text carries "Gemaakt door AI. Controleer of het klopt."; a deadline or amount below the server's threshold shows an orange "Controleer dit goed" label with an icon.
- **A value read from the letter is judged on its source** (sender, letter date, deadline): "Controleer dit goed" when the server sets `needs_attention`, the confidence is below 0.85 (the server's `NEEDS_ATTENTION_BELOW` for deadlines and amounts) or there is no quote. What the AI wrote itself (document type, task type, task description) gets the mark only when the server flags it: the server gives those a fixed confidence of 0.5 and no quote, so judging them the same way put a mark on every such field of every letter (seen in the simulator, 15-11-2026) and the mark stopped meaning anything; the banner "Ingevuld door AI" covers them. Also: confidence 0 is never pre-filled but shown as "Voorstel van AI, niet teruggevonden in de brief"; every pre-filled value with a quote has its own "Waar staat dit?". The pay task the app adds for an invoice due date says "Niet gecontroleerd" on its type and text (not read from the letter); only its date has a source. Amounts (`invoice_amount_incl`) and `invoice_number` are not shown or confirmed: the confirm contract has no field for them.
- **A changed value is the user's own.** The draft keeps each pre-filled value's origin (value, quote, mark); quote and mark show only while the field still holds that exact value, so changing it hides both and typing the original back restores them. The deadline's `deadline_source`/`deadline_quote` sent on confirm follow the same rule.
- "Post toevoegen" is a menu with the scanner and "Kies foto's" (photos of the pages): the scanner reports itself as supported in the simulator but has no camera there, and a photo of a letter is a real way in too.
- File paths are built with `path(percentEncoded: false)`: the default percent-encodes the space in `Application Support`, and the queue then finds nothing (caught in the simulator; a test now uses a directory with a space).

## Fixes after the whole-branch reviews (phase 1b)

- **A scan belongs to one server.** A queued item stores `ServerConnection.serverID` (the pinned CA's fingerprint, or the set of hosts without a private CA). After pairing with another server it is not sent: it fails with `server_changed` and can only be deleted. Pairing the same server again (new device id) sends it.
- **Every attempt has an id** (in the task description and on the item). An event of an earlier attempt, such as the late cancellation of a task the system ended, is ignored, so an item is never uploaded twice in parallel.
- **No pairing is not an untrusted server.** An upload that starts after the pairing was cleared (a 401 elsewhere) is paused and goes out after the next pairing, instead of failing as "not verified".
- **The system's completion handler** is also called when its events were handled before the app delegate handed it over. Every handler the system hands over is kept and called exactly once, on the main actor; an early delivery is used by the next handler only.
- **A scan with a page that could not be loaded is refused as a whole** (a photo only in iCloud, a scanner page without data), with "Een pagina kon niet worden gelezen": never uploaded with a page missing.
- **A scan on its way can be deleted**, and shows "Wacht op verbinding" until the first bytes are sent.
- **A review pre-filled by AI says so at the top** ("Ingevuld door AI. Controleer of het klopt voordat je bevestigt."), next to the label on the summary.
- **The paired app stays in the view tree while locked**, under an opaque lock screen, so a half-filled review survives a trip to another app. Sheets above it close when the scene leaves the foreground (the letter-text sheet and, since 1c, the person and label pickers and the calendar's "ook verwijderen?" question when inactive; the scanner and photo picker in the background), and polling stops while the app is not active. The review keeps that decision in its model (`ReviewModel.sceneDidChange(isActive:)`), so a test covers it.

## Organising (phase 1c)

- Persons and labels are loaded once per review screen, next to the document. When either list cannot be loaded, the screen behaves as against a 1b server: "Op naam van" and "Labels" are hidden and confirm sends `sets_organisation: false`, which leaves labels and addressees alone.
- Which proposal starts ticked comes from the server (`preselected`), so web and app agree; what an automatic rule already put on the letter starts chosen too.
- After confirming with the lists, every proposal the user did not choose is dismissed for good on that letter: nothing automatic proposes it there again.
- A person or label deleted while the review is open makes confirm answer "not found": the app reloads the lists, drops what is gone and keeps the rest of the draft. Only "not found" for the document itself leaves the review; any other failure while reloading keeps the draft and shows an error.
- **The `DocumentServer` seam grew** (persons, labels, suggestions, tasks) instead of a third seam. The fake (`FakeDocumentServer`, in `BrievieCore`) serves every test target, so one fake covers the post list, the review, the confirmed letter and the calendar; a third seam would have meant a second fake to keep equal.
- **A 1c app reads a 1b server.** People update the app before the server. Fields the server added in 1c are optional in the contract (host decision, `957e2e9`): missing lists read as empty, a missing inbox state is derived from the status (processing is new, needs review and failed are review, done is sorted). Against a 1b server the organise sections and the task tick boxes do not show.
- **Unknown values never break decoding** (API v1 is additive): an unknown inbox state is `.unknown`, an unknown suggestion action is dropped (not shown), an unknown origin is kept as unknown, an unknown label colour is grey.
- **Preselection comes from the server**; labels are created in the web only (the app picks, never creates or edits them; persons can be added in the review); there is no history or undo of rule actions in the app.
- **The post list** groups the inbox as "Te controleren", "Op niemands naam" and "Onderweg". "Onderweg" also holds scans that are still on the phone, which is why it is not called "Nieuw" as in the web. Persons and labels are fetched on the first load, on pull-to-refresh and on a scope change, not on the 3-second refresh. A slow answer for an earlier scope never touches the current one (also not its error). A person scope falls back to the inbox when that person is gone.
- **A confirmed letter** (name, labels, tasks): a change is sent at once, in tap order, built on the model's own state (not on what the screen showed when it was tapped). A failed change restores what the server last said. The task hook (`onTasksChanged`, which triggers the calendar sync) is held by the confirmed model, not by the review screen, so it survives the screen closing mid-tick.
- **A proposal always says "Voorstel"** next to its chip (text, not colour or opacity), also for a viewer who cannot tap it; VoiceOver says it too.
- **Label colours are defined in code** with a light and a dark value (`LabelChip`; `BrievieUI` has no asset catalog), text against fill at least 4.5:1 in both. A label always shows its name; colour is never the only signal.

## Unpair

- **"Ontkoppelen" on the Workspaces screen: best-effort server revoke, queue wiped, notice when the server could not be told.** `revokeDevice` (`DELETE /api/v1/devices/{id}` with the device token) gets 5 seconds over all the pairing's addresses; offline, no answer, a pin failure or any refusal never blocks unpairing. 401 and 404 `device_not_found` count as told (the server no longer knows the device). Then every upload is cancelled and the whole queue directory emptied (unreadable items and interrupted writes too), the stored connection and token are cleared (the `hasLaunchedBefore` flag stays), and pairing shows; only when the server was not told it says once "Deze telefoon staat nog als apparaat op de server. Trek hem daar in onder Apparaten." The confirmation names the number of waiting scans (catalog plural).
- **Revoked and unpaired end in one path** (`AppModel.finishForgetting`): empty the queue (unpair only), clear the store, show pairing. When a step fails the app stays locked and every activation and unlock attempt retries it; it never shows pairing with a token left in the Keychain. A 401 whose clear fails now stays locked too (before, it showed pairing anyway). The retry lives in memory: a killed app reopens on the stored pairing (unlock, then a 401 if the server was told).

## Storage

- **`UserDefaults`: one boolean, `hasLaunchedBefore`** — the first sanctioned use of `UserDefaults` (flag only, never secrets; behind the `LaunchFlag` protocol; the second is the calendar switch, see "Calendar (phase 1c)"). Keychain items survive uninstalling the app, `UserDefaults` does not, so a missing flag means "first launch after an install" and the app then clears the stored connection. Without this a reinstall would reopen a pairing the user thought was gone (deleting the app is not unpairing it). Consequence: a device restored from a backup (flag restored, Keychain items not) or a new device needs to pair again. Until the check has completed (protected data available, clear succeeded) the app stays on the lock screen and never unlocks a stored connection; it retries on every activation, unlock attempt and when protected data becomes available.

## Release

- **App icon and privacy manifest** — `scripts/make-app-icon.swift` draws the opaque 1024x1024 app icon: an envelope with a tick as its flap, on a navy square. `App/PrivacyInfo.xcprivacy` declares no tracking and no collected data, and only the `UserDefaults` required-reason API (`CA92.1`: the `hasLaunchedBefore` flag and, since 1c, the calendar identifier per workspace); a grep found no other required-reason APIs.

- **Bundle id `nl.stijnvdpol.brievie`** — chosen by the owner on 2026-11-14; fixed after the first upload. The Keychain service default and the test identifiers follow it (nothing was released yet, so no migration).

- **`Brievie.xcodeproj` is committed** — Xcode Cloud builds from the repository and needs the project, the shared scheme and `Package.resolved`. `project.yml` stays the source; `make check-project` (in CI) fails when the committed project differs. The team id lives in `Base.xcconfig` (not a secret). `ci_scripts/ci_post_clone.sh` disables package plugin validation for the OpenAPI generator.

With a pinned private CA the redirect target must still present a certificate of that CA, so the scan cannot leave the server; with a public certificate (no pin) a 307/308 could carry the scan to another host. ## Follow-ups (2026-11-17)

- **The inbox comes from the server per state.** One `listDocuments` per inbox state (`inbox_state` review, unassigned, new, side by side) plus `getInboxCounts` for the headers; a group that shows fewer letters than its count says "Te controleren (212, de nieuwste 200)". A list shorter than the server's limit (200) is the whole state, so its own length wins over a count. A 1b server ignores the filter (each list keeps only letters whose derived state matches) and has no counts (the header counts what is shown). The 3-second tick asks only for the "new" list, and only once the inbox is loaded (still loading or failed: it loads the whole inbox, so a tick never shows half an inbox or hides an error). The whole inbox is loaded once when a letter left the "new" list, or when a scan left the upload queue and is nowhere in the inbox (the server read it to review within one tick, so the phone never saw it as "new"). Inbox and "Alle post" no longer share a list: switching between them starts empty. A slow answer for an earlier scope never touches the current one, and loads are numbered: only the latest writes, so an older answer for the same scope never overwrites a newer one.
- **Unpairing can remove the calendars.** With a calendar switch on, the confirmation also offers "Ontkoppelen en agenda's verwijderen": each workspace's calendar goes through `CalendarSync.disable(removeCalendar: true)` before the local state is wiped, best effort. The removal runs in its own task and unpairing waits for it at most the unpair timeout (5 s): a sync that holds a workspace's calendar longer, or a failure, never blocks unpairing. A removal that finishes after the wipe finds the switches cleared and removes or writes nothing; that calendar then stays ("Ontkoppelen" keeps them all, as before).
- **A revocation (401) clears the calendar switches** (`AppModel` clears them with the pairing); the calendars stay.
- **"Verwijderen" never deletes the user's own events.** Before removing, the store checks the whole calendar from 2000 through 2100 (in three-year slices; EventKit searches at most four years at a time) for an event without a `brievie://task/` link. When there is one, only Brievie's events go, the calendar stays and the switch says "In deze agenda staan ook afspraken van jou. De agenda blijft staan; de afspraken van Brievie zijn weg."
- **Choosing a calendar is one step across all workspaces.** Reading the other workspaces' calendars, `ensureCalendar` and storing the id run as one critical section in `CalendarSync` (a queue of tasks, not a lock), also in a sync that makes a deleted calendar again. `CalendarSettings` counts its clears: turning a switch on stores the calendar only when no unpair (or revocation) cleared the settings since it started.
- **Titles:** the screen of a confirmed letter is "Brief" ("Controleren" while it is in review or loading); the calendar switch no longer repeats the workspace's name as a subtitle.
- **A confirmed letter loads its persons and labels again** each time it is loaded (a label made in the web shows in the picker); lists that cannot be loaded keep the ones on screen. A letter in review still asks for them once.

## Calendar (phase 1c)

- **EventKit on the phone, not an ICS feed from the server** (owner decision, design section 16). A feed would need a URL a calendar service can reach, with a secret in it, from outside the home network; the self-hosted server usually is not reachable that way and should not have to be. EventKit keeps everything on the phone: the server sends nothing to any calendar service.
- **Full access (`NSCalendarsFullAccessUsageDescription`, `requestFullAccessToEvents`).** Write-only access cannot read events back, so the app could not find, move or delete the events it made. Write-only, restricted and denied all count as no access: the switch goes back off with "Geef Brievie toegang tot je agenda in Instellingen." and "Open Instellingen". Against a server without a task list (a 1b server: an unknown API path answers 404 `not_found`, read as `DocumentsError.notSupported`) the switch reads the tasks before it asks for calendar access or makes a calendar, so no system prompt appears and no calendar is made; it goes back off and says "Deze server kan nog geen taken doorgeven. Werk de server bij."
- **One calendar per workspace, made by the app: "Brievie – <werkruimte>"**, in the source of the phone's default calendar; when there is none or it takes no new calendar, the iCloud source, then the local one; never another CalDAV, Exchange or subscribed account (the task's text and sender would land on a third party's server), else a clear error. A default calendar in Exchange or Google is still used: that default is the user's own choice. The EventKit store is reset once after access is granted, because a store made before the grant can keep answering without calendars. Every sync sets the title of the calendar it holds back to "Brievie – <werkruimte>" (a renamed workspace, or a title the user changed), best effort: a failing rename never fails the sync. It is the only calendar the app writes in, and only while that workspace's switch is on. Turning the switch off asks whether to delete that calendar too ("Verwijderen" / "Laten staan"); nothing else is ever deleted, and a calendar that also holds events of the user is never deleted (see "Follow-ups (2026-11-17)"). A calendar the user deleted is made again by the next sync. An existing calendar with the same title is taken over (switching on again, pairing again) only when it is in the default calendar source, no other workspace holds it, and it has no event without a task link in the window; otherwise a new one is made, even with the same title. So two workspaces with the same name get two calendars, and a calendar the user made never becomes Brievie's. Without the workspace's name (not loaded yet) no calendar is made.
- **The calendar is the state.** No local table of task and event: every sync reads the open tasks from the server and the events of the calendar, and a pure planner (`CalendarSyncPlanner`) returns what to create, update and delete, matched on the event's URL `brievie://task/<id>`. Events without such a URL (added by the user) are never touched; duplicates of one task are deleted down to one. One all-day event per open task with a deadline, alarms at 09:00 local time 7 days before, 2 days before and on the day (relative offsets from the event's start, so a change to or from summer time in between moves an alarm by an hour). Only events with a task link are ever changed or deleted. The `brievie` URL scheme is registered; opening a `brievie://task/...` link only opens the app (lock first): no navigation to the task in 1c, nothing is read from the link.
- **Window: one year back to 30 days short of three years ahead** (`CalendarDate` arithmetic, never a `Date` at midnight). EventKit searches at most four years at a time; the query of the whole window plus a day stays clearly under that. A deadline further away gets its event once it comes inside the window, and the event of a task whose deadline moved out of it is deleted.
- **Syncs run when the Workspaces list loads (when it first appears, on every later unlock, on every return to the Workspaces screen and on pull-to-refresh), after a confirm and after ticking a task off or opening it again.** A sync for a workspace whose switch is off does nothing, so the extra loads cost one read of the open tasks per switch that is on. Work for one workspace never runs twice at once (`CalendarSync` lets a second call wait for the first), and a sync never writes a calendar identifier back after unpairing cleared it. No background sync: a deadline confirmed on another device appears the next time this app opens. The same list load checks calendar access: a switch that is on while access was taken away in Settings stays on and says "Geef Brievie toegang tot je agenda in Instellingen." with "Open Instellingen"; syncing resumes by itself when access is back.
- **`UserDefaults`: the second sanctioned use, the calendar switch per workspace** (`calendar.<workspace-uuid>` = the calendar's identifier; not a secret), behind the `CalendarSettings` protocol. Forgetting the pairing clears these keys: "Ontkoppelen" and, since 2026-11-17, a revocation by the server (a 401), so the switches never come back on by themselves after pairing again. The calendars stay unless the user chose "Ontkoppelen en agenda's verwijderen" (see "Follow-ups (2026-11-17)"); a calendar that stays keeps firing its alarms until the user deletes it (pairing again takes it over under the rule above). The privacy manifest's `CA92.1` reason covers it (the app's own defaults).
- **The events go wherever that calendar syncs** (usually iCloud), with the task's text and the sender in them; the footer under each switch says so and names that workspace's calendar. That is the user's choice per phone.
