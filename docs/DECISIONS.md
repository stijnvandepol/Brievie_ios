# Decisions

One line per dependency or tooling choice, with the reason.

## Tooling

- **XcodeGen** — the Xcode project is generated from `project.yml`, so `*.xcodeproj` never causes merge conflicts.
- **SwiftLint** (`--strict`, `force_unwrapping` on) — the lint gate locally and in CI.
- **Swift Testing** — the test framework for all targets; ships with the toolchain, no package dependency.
- **CodeQL** (`.github/workflows/codeql.yml`, `security-extended`) — static analysis of the Swift code (manual build mode: `make build`, so the app and `BrievieKit` are compiled and analysed; CodeQL supports Swift 5.4 to 6.3 and needs macOS) and of the workflows themselves. Runs on pushes to `main`, pull requests and weekly; results go to GitHub code scanning. Third-party actions are pinned to commit SHAs; Dependabot moves them.
- **Dependabot for Swift packages** — weekly, grouped, for `Packages/BrievieKit`. A pull request must be completed with `make generate` (the copy of `Package.resolved` in the Xcode project); CI fails until then. `swift-openapi-generator` is ignored (pinned on purpose, see below).
- **Code coverage** — `make coverage` runs the same tests with `swift test --enable-code-coverage`; `scripts/coverage-summary.sh` prints line coverage per `BrievieKit` target and CI uploads the table and the JSON report as the `coverage` artifact. Tooling that ships with the toolchain and `python3`, no new dependency. There is no minimum yet; the place for one is marked in the script.

## Package dependencies

Versions checked on 2026-11-13 against the GitHub tags; exact resolutions are in `Packages/BrievieKit/Package.resolved`.

- **swift-openapi-runtime** `from: 1.13.4` (newest) — runtime for the generated client; `BrievieCore` imports it only to unwrap `ClientError`.
- **swift-openapi-urlsession** `from: 1.4.0` (newest) — `URLSession` transport, so trust is decided by our own session delegate.
- **swift-http-types** `from: 1.8.0` (newest) — already a dependency of the OpenAPI packages; declared explicitly because `APIClient.swift` imports `HTTPTypes` for the bearer-token middleware.
- **swift-openapi-generator** `exact: 1.12.2` (newest is 1.14.4) — build plugin in `BrievieAPI` that generates types and client from `openapi.json` (`generate: [types, client]`, `accessModifier: public`, `namingStrategy: idiomatic`). Pinned below the newest release on purpose: from 1.13.0 the generator emits `public import` lines, and from 1.13.1 it also splits types into files that do not use all of them, which gives "public import ... was not used" warnings on Swift 6.3 (Xcode 26.4); upstream only silences them from Swift 6.4 (`@diagnose`, PR #947). 1.12.2 output compiles warning-free under Swift 6 with complete strict concurrency, so no setting is relaxed for `BrievieAPI`. Move to the newest release once the toolchain is Swift 6.4. Build-time only: nothing of the generator ships in the app.
- **Generator `filter`** — only the operations the app calls (`getHealth`, `getCaCertificate`, `pairDevice`, `revokeDevice`, `listWorkspaces`); a feature that needs another operation adds it to `openapi-generator-config.yaml`. This keeps the generated surface small and avoids generating schemas the app does not use.

## API client

- The contract's paths already include `/api/v1`, so the generated client's server URL is the plain server address from the QR code.
- `APIClient.make(baseURL:session:token:)` takes a `URLSession` rather than a `ServerTrust`: `ServerTrust` lives in `BrievieCore`, which depends on `BrievieAPI`, so `BrievieAPI` cannot name it. `LiveBrievieServer` (in `BrievieCore`) builds the pinned session, passes it in, and invalidates it after each call.
- `openapi.json` is a verbatim copy of the host's file (`make sync-api`), never edited by hand; `API_VERSION` holds its `info.version`.
- Phase 1b adds `listDocuments`, `getDocument`, `getDocumentPage`, `confirmDocument` and `retryDocumentProcessing` to the generator `filter`, plus the schema `UploadMetadataIn`: the JSON in the `metadata` field of the multipart upload, which goes through a background `URLSession` instead of the generated client. Nullable fields arrive as Swift optionals since the host writes them as type arrays (host decision 2026-11-14); a `date` stays a `String` in the generated types.
- `FlexibleDateTranscoder` reads timestamps with and without fractional seconds: the host (Pydantic) sends a fraction unless the time falls on a whole second, and the runtime's default transcoder accepts only the form without.
- Every session `LiveBrievieServer` uses refuses redirects (`PinnedSessionDelegate` and the one-off CA delegate): the API never redirects, and a followed redirect could carry the `Authorization` header or the pairing code to another host.
- Server error codes reach the app only from a closed set (`ServerError.passThroughCodes`, plus the codes mapped to their own cases); anything else becomes `http_<status>`. `ServerError.other` and `PairingError.failed` are diagnostic only and never shown to the user.


## Scanning (phase 1b)

- **VisionKit document scanner + Apple Vision text recognition, on the device** (owner decision 2026-11-14): the app is the only intake in 1b and the server runs no OCR. No new package dependency: VisionKit, Vision, ImageIO and PhotosUI ship with iOS.
- `VisionTextRecognizer` uses `RecognizeTextRequest` (accurate, language correction) with Dutch when the system lists a language with code `nl` (it does on macOS 26 / iOS 26: `nl-Latn-NL`), otherwise automatic detection. Lines are ordered top to bottom, then left to right.
- Pages are uploaded as JPEG, longest edge 2400 px, quality 0.7 (`PageImageEncoder`). Scanner pages and library photos are handed over as compressed data and decoded one at a time, already scaled down (ImageIO thumbnail with transform, which also applies the EXIF orientation), so a 30-page scan never sits in memory as full-size bitmaps.
- `PhotoImportButton` (PhotosPicker) is the way in where the scanner is unavailable (simulator, no camera).
- The test letter (`Tests/BrievieScanTests/Fixtures/letter-nl.png`) is drawn by `make-letter.swift` next to it.

## Upload queue (phase 1b)

- **One directory per queued document, not SwiftData.** `Application Support/Uploads/<id>/` holds `item.json` (the record) and `body.multipart` (the ready-to-send request body). The spec names SwiftData for the queue; a record next to its body is less code, the two disappear together, and a background upload needs the body as a file anyway. Reconsider for the document cache (1c).
- An item is written under `.incoming-<id>` and renamed when complete, so a crash never leaves half an item; leftovers are removed at start. A directory whose `item.json` is missing or not an item can never be uploaded: it is removed at start and the post list says once "1 scan kon niet worden gelezen en is verwijderd". A record that exists but cannot be opened yet (before the first unlock) is kept. The queue is excluded from backup and readable after the first unlock (the background upload reads it while the phone is locked).
- The item's id is the document's `client_id` on the server: a repeated upload finds the same document.
- Server limits are checked on the phone (`UploadLimits.server`: 30 pages, 32 MiB, 20000 Unicode code points of text per page, as the host counts them; longer text is cut between whole characters), so a scan that cannot succeed is never queued.

## Background upload (phase 1b)

- **One background `URLSession` per process** (`nl.stijnvdpol.brievie.upload`), created at launch, also when the system relaunches the app for finished uploads. Its own configuration instead of `SessionConfiguration.hardened`: that one's 30 s resource timeout would end every slow upload; here the system waits for a connection itself (up to 7 days per attempt). No cookies, no cache, no stored credentials, redirects refused.
- **Trust is read per TLS handshake** (`UploadTrustProvider`): the session outlives a pairing, so the pin comes from the stored connection each time. Without a readable pairing the connection is refused; there is no fallback to system trust for a pinned server.
- **The device token travels in the request of a background task**, which iOS keeps outside the app's process until the task ends. Accepted for now; a short-lived upload token is later hardening.
- **Swiping the app away cancels its background uploads** (iOS design). They stay in the queue and go out the next time the app opens. When the system itself ends the app, uploads continue. Such a cancellation counts as "unreachable", never as a failure; only our own refusal of the server's certificate is "untrusted".
- **Retry rules** live in `UploadPolicy` (pure): next URL at once, then back to the first with a backoff of 30 s up to 1 hour, forever; 401 pauses the queue and sends the user to pairing, nothing is deleted; other 4xx answers fail the item with a code from a closed set, and the user can retry or delete it.
- `AppModel` does not know the queue: `AppEnvironment.live` builds transport and coordinator, `RootView` calls `resume()` whenever the app becomes ready.

## Documents (phase 1b)

- **A second seam, `DocumentServer`**, next to `BrievieServer`: the document calls (`documents`, `document`, `pageImage`, `confirm`, `retryProcessing`) take a `DocumentScope` (address, trust, token, workspace). `LiveBrievieServer` implements both. Adding five methods to `BrievieServer` would have forced every pairing fake to grow with them.
- **`WorkspaceDocuments`** is what screens use: it tries the pairing's addresses in order, reads the token from the Keychain, and sorts every failure into a `DocumentsError` (revoked, unreachable, not verified, not found, conflict, ...).
- **`CalendarDate`** (year, month, day) for letter dates and deadlines, never `Date`: a deadline is a day, and a `Date` at midnight in Amsterdam is the day before in Los Angeles.
- A page image is read with a 20 MiB cap; `FakeDocumentServer` and `DocumentFixtures` live in `BrievieCore` because several test targets use them.

## Document list and scanning screens (phase 1b)

- `FeatureDocuments` holds the post of a workspace (`DocumentsModel`, `DocumentsView`) and the scan flow (`ScanFlowModel`). A workspace row opens it through a destination the app supplies (`WorkspacesView(destination:)`), so `FeatureWorkspace` does not depend on it. The tab bar of spec section 13 comes in 1c with the Today screen.
- Screens talk to the queue through the `UploadQueue` protocol (`UploadCoordinator` conforms); a scan on the phone and its document on the server (same id as `client_id`) are one row.
- The list refreshes every 3 seconds only while something is on its way (waiting, uploading, processing) and the screen is visible. There is no push in phase 1.
- All visible text of this target is in `DocumentStrings` (catalog key plus the Dutch default), also for views; the parity test keeps catalog and code equal. A viewer, or a role this app does not know, gets no scan button.

## Review screen (phase 1b)

- `ReviewModel` turns the server's proposals into a draft: a value the letter does not support (confidence 0) is shown as a hint, never pre-filled; a deadline the user changes becomes `manual` and loses its quote, so the source shown always belongs to the value; an invoice due date without a payment action adds a "Betaal de rekening" task. Nothing is sent before "Bevestigen".
- "Waar staat dit?" shows the letter text with the quote marked (`QuoteLocator`: ignores case, accents and line breaks; it only finds what to highlight). Marking the place on the page image needs text positions from Vision: later.
- AI-written text carries "Gemaakt door AI. Controleer of het klopt."; a deadline or amount below the server's threshold shows an orange "Controleer dit goed" label with an icon.
- **A value read from the letter is judged on its source** (sender, letter date, deadline): "Controleer dit goed" when the server sets `needs_attention`, the confidence is below 0.85 (the server's `NEEDS_ATTENTION_BELOW` for deadlines and amounts) or there is no quote. What the AI wrote itself (document type, task type, task description) gets the mark only when the server flags it: the server gives those a fixed confidence of 0.5 and no quote, so judging them the same way put a mark on every such field of every letter (seen in the simulator, 15-11-2026) and the mark stopped meaning anything; the banner "Ingevuld door AI" covers them. Also: confidence 0 is never pre-filled but shown as "Voorstel van AI, niet teruggevonden in de brief"; every pre-filled value with a quote has its own "Waar staat dit?". The pay task the app adds for an invoice due date says "Niet gecontroleerd" on its type and text (not read from the letter); only its date has a source. Amounts (`invoice_amount_incl`) and `invoice_number` are not shown or confirmed: the confirm contract has no field for them.
- **A changed value is the user's own.** The draft keeps each pre-filled value's origin (value, quote, mark); quote and mark show only while the field still holds that exact value, so changing it hides both and typing the original back restores them. The deadline's `deadline_source`/`deadline_quote` sent on confirm follow the same rule.
- "Post toevoegen" is a menu with the scanner and "Kies foto's" (photos of the pages): the scanner reports itself as supported in the simulator but has no camera there, and a photo of a letter is a real way in too.
- File paths are built with `path(percentEncoded: false)`: the default percent-encodes the space in `Application Support`, and the queue then finds nothing (caught in the simulator; a test now uses a directory with a space).

## Fixes after the whole-branch reviews (phase 1b)

- **A scan belongs to one server.** A queued item stores `ServerConnection.serverID` (the pinned CA's fingerprint, or the set of hosts without a private CA). After pairing with another server it is not sent: it fails with `server_changed` and can only be deleted. Pairing the same server again (new device id) sends it.
- **Every attempt has an id** (in the task description and on the item). An event of an earlier attempt, such as the late cancellation of a task the system ended, is ignored, so an item is never uploaded twice in parallel.
- **No pairing is not an untrusted server.** An upload that starts after the pairing was cleared (a 401 elsewhere) is paused and goes out after the next pairing, instead of failing as "not verified".
- **The system's completion handler** is also called when its events were handled before the app delegate handed it over. Every handler the system hands over is kept and called exactly once, on the main actor; an early delivery is used by the next handler only.
- **A scan with a page that could not be loaded is refused as a whole** (a photo only in iCloud, a scanner page without data), with "Een pagina kon niet worden gelezen": never uploaded with a page missing.
- **A scan on its way can be deleted**, and shows "Wacht op verbinding" until the first bytes are sent.
- **A review pre-filled by AI says so at the top** ("Ingevuld door AI. Controleer of het klopt voordat je bevestigt."), next to the label on the summary.
- **The paired app stays in the view tree while locked**, under an opaque lock screen, so a half-filled review survives a trip to another app. Sheets above it close when the scene leaves the foreground (the letter-text sheet and, since 1c, the person and label pickers and the calendar's "ook verwijderen?" question when inactive; the scanner and photo picker in the background), and polling stops while the app is not active. The review keeps that decision in its model (`ReviewModel.sceneDidChange(isActive:)`), so a test covers it.

## Organising (phase 1c)

- Persons and labels are loaded once per review screen, next to the document. When either list cannot be loaded, the screen behaves as against a 1b server: "Op naam van" and "Labels" are hidden and confirm sends `sets_organisation: false`, which leaves labels and addressees alone.
- Which proposal starts ticked comes from the server (`preselected`), so web and app agree; what an automatic rule already put on the letter starts chosen too.
- After confirming with the lists, every proposal the user did not choose is dismissed for good on that letter: nothing automatic proposes it there again.
- A person or label deleted while the review is open makes confirm answer "not found": the app reloads the lists, drops what is gone and keeps the rest of the draft. Only "not found" for the document itself leaves the review; any other failure while reloading keeps the draft and shows an error.
- **The `DocumentServer` seam grew** (persons, labels, suggestions, tasks) instead of a third seam. The fake (`FakeDocumentServer`, in `BrievieCore`) serves every test target, so one fake covers the post list, the review, the confirmed letter and the calendar; a third seam would have meant a second fake to keep equal.
- **A 1c app reads a 1b server.** People update the app before the server. Fields the server added in 1c are optional in the contract (host decision, `957e2e9`): missing lists read as empty, a missing inbox state is derived from the status (processing is new, needs review and failed are review, done is sorted). Against a 1b server the organise sections and the task tick boxes do not show.
- **Unknown values never break decoding** (API v1 is additive): an unknown inbox state is `.unknown`, an unknown suggestion action is dropped (not shown), an unknown origin is kept as unknown, an unknown label colour is grey.
- **Preselection comes from the server**; labels are created in the web only (the app picks, never creates or edits them; persons can be added in the review); there is no history or undo of rule actions in the app.
- **The post list** groups the inbox as "Te controleren", "Op niemands naam" and "Onderweg" (replaced by one list on 2026-11-19, see "Te doen and Alle post"). "Onderweg" also holds scans that are still on the phone, which is why it is not called "Nieuw" as in the web. Persons and labels are fetched on the first load, on pull-to-refresh and on a scope change, not on the 3-second refresh. A slow answer for an earlier scope never touches the current one (also not its error). A person scope falls back to the inbox when that person is gone.
- **A confirmed letter** (name, labels, tasks): a change is sent at once, in tap order, built on the model's own state (not on what the screen showed when it was tapped). A failed change restores what the server last said. The task hook (`onTasksChanged`, which triggers the calendar sync) is held by the confirmed model, not by the review screen, so it survives the screen closing mid-tick.
- **A proposal always says "Voorstel"** next to its chip (text, not colour or opacity), also for a viewer who cannot tap it; VoiceOver says it too.
- **Label colours are defined in code** with a light and a dark value (`LabelChip`; `BrievieUI` has no asset catalog), text against fill at least 4.5:1 in both. A label always shows its name; colour is never the only signal.

## Unpair

- **"Ontkoppelen" on the Workspaces screen: best-effort server revoke, queue wiped, notice when the server could not be told.** `revokeDevice` (`DELETE /api/v1/devices/{id}` with the device token) gets 5 seconds over all the pairing's addresses; offline, no answer, a pin failure or any refusal never blocks unpairing. 401 and 404 `device_not_found` count as told (the server no longer knows the device). Then every upload is cancelled and the whole queue directory emptied (unreadable items and interrupted writes too), the stored connection and token are cleared (the `hasLaunchedBefore` flag stays), and pairing shows; only when the server was not told it says once "Deze telefoon staat nog als apparaat op de server. Trek hem daar in onder Apparaten." The confirmation names the number of waiting scans (catalog plural).
- **Revoked and unpaired end in one path** (`AppModel.finishForgetting`): empty the queue (unpair only), clear the store, show pairing. When a step fails the app stays locked and every activation and unlock attempt retries it; it never shows pairing with a token left in the Keychain. A 401 whose clear fails now stays locked too (before, it showed pairing anyway). The retry lives in memory: a killed app reopens on the stored pairing (unlock, then a 401 if the server was told).

## Storage

- **`UserDefaults`: one boolean, `hasLaunchedBefore`** — the first sanctioned use of `UserDefaults` (flag only, never secrets; behind the `LaunchFlag` protocol; the second is the calendar switch, see "Calendar (phase 1c)"). Keychain items survive uninstalling the app, `UserDefaults` does not, so a missing flag means "first launch after an install" and the app then clears the stored connection. Without this a reinstall would reopen a pairing the user thought was gone (deleting the app is not unpairing it). Consequence: a device restored from a backup (flag restored, Keychain items not) or a new device needs to pair again. Until the check has completed (protected data available, clear succeeded) the app stays on the lock screen and never unlocks a stored connection; it retries on every activation, unlock attempt and when protected data becomes available.

## Release

- **App icon and privacy manifest** — `scripts/make-app-icon.swift` draws the opaque 1024x1024 app icon: an envelope with a tick as its flap, on a navy square. `App/PrivacyInfo.xcprivacy` declares no tracking and no collected data, and only the `UserDefaults` required-reason API (`CA92.1`: the `hasLaunchedBefore` flag and, since 1c, the calendar identifier per workspace); a grep found no other required-reason APIs.

- **Bundle id `nl.stijnvdpol.brievie`** — chosen by the owner on 2026-11-14; fixed after the first upload. The Keychain service default and the test identifiers follow it (nothing was released yet, so no migration).

- **`Brievie.xcodeproj` is committed** — Xcode Cloud builds from the repository and needs the project, the shared scheme and `Package.resolved`. `project.yml` stays the source; `make check-project` (in CI) fails when the committed project differs. The team id lives in `Base.xcconfig` (not a secret). `ci_scripts/ci_post_clone.sh` disables package plugin validation for the OpenAPI generator.

## Follow-ups (2026-11-17)

- **The inbox comes from the server per state.** One `listDocuments` per inbox state (`inbox_state` review, unassigned, new, side by side) plus `getInboxCounts` for the headers; a group that shows fewer letters than its count says "Te controleren (212, de nieuwste 200)". A list shorter than the server's limit (200) is the whole state, so its own length wins over a count. A 1b server ignores the filter (each list keeps only letters whose derived state matches) and has no counts (the header counts what is shown). The 3-second tick asks only for the "new" list, and only once the inbox is loaded (still loading or failed: it loads the whole inbox, so a tick never shows half an inbox or hides an error). The whole inbox is loaded once when a letter left the "new" list, or when a scan left the upload queue and is nowhere in the inbox (the server read it to review within one tick, so the phone never saw it as "new"). Inbox and "Alle post" no longer share a list: switching between them starts empty. A slow answer for an earlier scope never touches the current one, and loads are numbered: only the latest writes, so an older answer for the same scope never overwrites a newer one. A tick is skipped while a full load (first load, pull-to-refresh, the load after a scan, retry or delete) is still running: that load asks for "new" too, and a newer tick would make it lose; a full load that starts after a tick wins over it, which is right because it is a superset. A scan counts as having left the queue also when it only joined the queue at this load's own read.
- **Unpairing can remove the calendars.** With a calendar switch on, the confirmation also offers "Ontkoppelen en agenda's verwijderen": each workspace's calendar goes through `CalendarSync.disable(removeCalendar: true)` before the local state is wiped, best effort. The removal runs in its own task and unpairing waits for it at most the unpair timeout (5 s): a sync that holds a workspace's calendar longer, or a failure, never blocks unpairing. A removal that runs after the wipe sees that the settings were cleared since it started (their clear generation changed) and removes or writes nothing, also when the user paired again and switched the same workspace on meanwhile; that calendar then stays ("Ontkoppelen" keeps them all, as before).
- **A revocation clears the calendar switches and removes their calendars without asking** (security review 2026-11-17; before, the calendars stayed): a revoked phone may be a stolen one. Only a 401 with the host's own code `not_authenticated` is a revocation: a 401 from something in front of the server (a reverse proxy's login, a non-JSON body) is `http_401`, an ordinary error that forgets nothing and removes nothing (this also changed what forgets the pairing, not only the calendars). `AppModel` first stores the calendars to remove (`calendarPendingRemoval.<calendar-id>`, which clearing the switches leaves alone), then clears the switches, then `CalendarSync.removePendingRemovals` removes each under the same rule as "Verwijderen": a calendar that also holds the user's own events stays and loses only the events with a Brievie link. Without full calendar access `removeCalendar` throws (EventKit then sees no calendars at all, which is not "gone"), so a calendar stays marked until a removal with access succeeded; every activation tries again, also in a new process. A calendar a new pairing took over meanwhile is left alone. A revocation that arrives while an "Ontkoppelen" is still pending keeps that unpair's choice about the calendars.
- **"Verwijderen" never deletes the user's own events.** Before removing, the store checks the whole calendar from 2000 through 2100 (in three-year slices; EventKit searches at most four years at a time) for an event without a `brievie://task/` link. When there is one, only Brievie's events go, the calendar stays and the switch says "In deze agenda staan ook afspraken van jou. De agenda blijft staan; de afspraken van Brievie zijn weg."
- **Choosing a calendar is one step across all workspaces.** Reading the other workspaces' calendars, `ensureCalendar` and storing the id run as one critical section in `CalendarSync` (a queue of tasks, not a lock), also in a sync that makes a deleted calendar again. `CalendarSettings` counts its clears: turning a switch on stores the calendar only when no unpair (or revocation) cleared the settings since it started.
- **Titles:** the screen of a confirmed letter is "Brief" ("Controleren" while it is in review or loading); the calendar switch no longer repeats the workspace's name as a subtitle.
- **A confirmed letter loads its persons and labels again** each time it is loaded (a label made in the web shows in the picker); lists that cannot be loaded keep the ones on screen. A letter in review still asks for them once.

## Calendar (phase 1c)

- **EventKit on the phone, not an ICS feed from the server** (owner decision, design section 16). A feed would need a URL a calendar service can reach, with a secret in it, from outside the home network; the self-hosted server usually is not reachable that way and should not have to be. EventKit keeps everything on the phone: the server sends nothing to any calendar service.
- **Full access (`NSCalendarsFullAccessUsageDescription`, `requestFullAccessToEvents`).** Write-only access cannot read events back, so the app could not find, move or delete the events it made. Write-only, restricted and denied all count as no access: the switch goes back off with "Geef Brievie toegang tot je agenda in Instellingen." and "Open Instellingen". Against a server without a task list (a 1b server: an unknown API path answers 404 `not_found`, read as `DocumentsError.notSupported`) the switch reads the tasks before it asks for calendar access or makes a calendar, so no system prompt appears and no calendar is made; it goes back off and says "Deze server kan nog geen taken doorgeven. Werk de server bij."
- **One calendar per workspace, made by the app: "Brievie – <werkruimte>"**, made without asking only in iCloud or the local source ("Op mijn iPhone"): the default calendar's account when it is one of those, else iCloud, else the local one (`CalendarSourceChoice`). Any other account (an employer's Exchange, Google, any CalDAV server) is run by someone who can read what is in it, also when it holds the default calendar (security review 2026-11-17; this replaces "the default is the user's choice"): the app makes a calendar there only after asking once, by that account's title ("Brievie zet je taken in de agenda van <account>. Wie die account beheert, kan ze lezen."), and an explicit yes; no, or leaving the app, keeps the switch off. Without any account the switch says so. The account is stored with the switch (`calendarSource.<workspace-uuid>`). The EventKit store is reset once after access is granted, because a store made before the grant can keep answering without calendars. Every sync sets the title of the calendar it holds back to "Brievie – <werkruimte>" (a renamed workspace, or a title the user changed), best effort: a failing rename never fails the sync. It is the only calendar the app writes in, and only while that workspace's switch is on. Turning the switch off asks whether to delete that calendar too ("Verwijderen" / "Laten staan"); nothing else is ever deleted, and a calendar that also holds events of the user is never deleted (see "Follow-ups (2026-11-17)"). A calendar the user deleted is made again by the next sync, in the account it was in and nowhere else; when that account is gone (removed from the phone, signed out of iCloud) the switch goes off for that workspace and says so. A switch stored before the account was (never on a device) may only be made again in iCloud or the local source. An existing calendar with the same title is taken over (switching on again, pairing again) only when it is in the account chosen for the new calendar, no other workspace holds it, and it has no event without a task link in the window; otherwise a new one is made, even with the same title. So two workspaces with the same name get two calendars, and a calendar the user made never becomes Brievie's. Without the workspace's name (not loaded yet) no calendar is made.
- **The calendar is the state.** No local table of task and event: every sync reads the open tasks from the server and the events of the calendar, and a pure planner (`CalendarSyncPlanner`) returns what to create, update and delete, matched on the event's URL `brievie://task/<id>`. Events without such a URL (added by the user) are never touched; duplicates of one task are deleted down to one. One all-day event per open task with a deadline, titled only "<taaksoort> (Brievie)" with "Uit Brievie" as notes unless the workspace's "Toon de omschrijving in de agenda" is on (see "Security fixes (2026-11-17)"), alarms at 09:00 local time 7 days before, 2 days before and on the day (relative offsets from the event's start, so a change to or from summer time in between moves an alarm by an hour). Only events with a task link are ever changed or deleted. The `brievie` URL scheme is registered; opening a `brievie://task/...` link only opens the app (lock first): no navigation to the task in 1c, nothing is read from the link.
- **Window: one year back to 30 days short of three years ahead** (`CalendarDate` arithmetic, never a `Date` at midnight). EventKit searches at most four years at a time; the query of the whole window plus a day stays clearly under that. A deadline further away gets its event once it comes inside the window, and the event of a task whose deadline moved out of it is deleted.
- **Syncs run when the Workspaces list loads (when it first appears, on every later unlock, on every return to the Workspaces screen and on pull-to-refresh), after a confirm and after ticking a task off or opening it again.** A sync for a workspace whose switch is off does nothing, so the extra loads cost one read of the open tasks per switch that is on. Work for one workspace never runs twice at once (`CalendarSync` lets a second call wait for the first), and a sync never writes a calendar identifier back after unpairing cleared it. No background sync: a deadline confirmed on another device appears the next time this app opens. Each switch runs its own sync after the list load (`CalendarSettingModel.refresh()`, after the app learned the names), so a sync that turned the switch off (the calendar's account is gone) shows it there. The same refresh checks calendar access first: a switch that is on while access was taken away in Settings stays on and says "Geef Brievie toegang tot je agenda in Instellingen." with "Open Instellingen"; syncing resumes by itself when access is back.
- **`UserDefaults`: the second sanctioned use, the calendar switch per workspace** (`calendar.<workspace-uuid>` = the calendar's identifier, `calendarSource.<workspace-uuid>` = its account's, `calendarDetails.<workspace-uuid>` = "Toon de omschrijving in de agenda", `calendarPendingRemoval.<calendar-id>` = the workspace of a calendar still to remove after a revocation; none a secret), behind the `CalendarSettings` protocol. Forgetting the pairing clears these keys (not the pending removals): "Ontkoppelen" and, since 2026-11-17, a revocation by the server (a 401 with the host's code `not_authenticated`), so the switches never come back on by themselves after pairing again. On "Ontkoppelen" the calendars stay unless the user chose "Ontkoppelen en agenda's verwijderen"; a revocation removes them (see "Follow-ups (2026-11-17)"); a calendar that stays keeps firing its alarms until the user deletes it (pairing again takes it over under the rule above). The privacy manifest's `CA92.1` reason covers it (the app's own defaults).
- **The footer under each switch names the calendar and where it is**: before it is on, "in iCloud of op deze iPhone" and that another account is used only with the user's yes; once on, the account (iCloud, "op deze iPhone", or the other account by its title with "Wie die account beheert, kan ze lezen.").

## Follow-ups to the security review (2026-11-17)

- **A calendar pending removal is never adopted.** `CalendarSync` excludes every `calendarPendingRemoval` id wherever it may adopt a calendar by title (switching on, and a sync that makes a deleted calendar again), so after a revocation and pairing again a workspace with the same name gets a new calendar. Chosen over running the removal inside the calendar-choice queue: that only orders the two steps, and a removal that wins the race still deletes a calendar the user is about to use; with the exclusion the calendar the user gets is never one the removal will delete, and the removal never waits on or blocks a choice.
- **The switch says "account gone" only when no switch-on is running.** `CalendarSettingModel` counts its running switch-ons; a refresh that started during one, or ends while one runs, does not read an off setting as "account gone" (a switch-on stores the setting at its end, or not at all after a question, no account or a failure). The proposed check "the setting was on when the refresh started" was not used: it would hide the case it was added for (a sync after a confirm that turned the setting off before the list load).
- **A 401 without `not_authenticated` is a passing error, never a revocation.** An upload waits and retries it with the usual backoff (30 s up to an hour, on the same address, like a 429 or 5xx) instead of failing until the user taps "Opnieuw"; the Workspaces list and every document call try the next address and, when none answers better, show the generic error ("Er ging iets mis. Probeer het opnieuw.").
- **Correction to the message of `536f6d9`** ("any 401 forgot the pairing, also one from a reverse proxy"): before that commit a 401 with a JSON body forgot the pairing on every path, but a 401 without one (a proxy's HTML login page) did so only for uploads, which read the status alone; the API calls failed on its content type with a generic error.


## Members and devices (phase 1d, part A)

- **The server link is only a pointer.** `brievie://server#v=1&url=…[&ca_sha256=…]&pairing=<uuid>` carries the server's addresses, its CA pin and the pairing code's id, form-encoded (`ServerLink`, parsed under the QR payload's rules: https only, no user info, at most eight addresses, a fragment of at most 4096 characters). A code in the link is never read.
- **Receiving a link contacts nothing until the user acts** (coordinator ruling, fix round 2). A link opens a sheet with one question, "Wil je deze telefoon koppelen aan een Brievie-server?", the button "Server zoeken" and "Sluit"; no address is listed (a list of addresses from someone else's link was the misleading part). Closing makes no request at all; a newer link before the tap replaces the older one, still without contact. Only the tap starts the search: the app then fetches the CA certificate (when the link has a pin) and the health answer from the link's addresses, nothing else. Nothing secret goes out (no code exists yet) and nothing is stored.
- **The address on screen is the address the proof goes to** (security review, fix round 1). After the tap the sheet says "Server zoeken…" and `PairingService.locate` walks the link's addresses as the QR path does (skipping what cannot be bound, CA pin and health with the same trust rules) and fixes the first one that answers. Only then does it show that address (ASCII as contacted, with a port other than 443, never a decoded Unicode name) and the code field; the challenge and the proof go to that address only, and a failure after the code is typed never moves on to another one (the user gets the refusal and can try again, or open the link again). No address answers: the unreachable sentence and no code field. This closes the hole where a hostile link showed a reassuring first address that was skipped or unreachable and then paired with its own host.
- **What a link pairing stores** (fix round 3). From a link without a pin only the located address is stored: later connections trust the system roots, so an extra address in someone else's link (own domain, valid public certificate) would otherwise receive the device token whenever the real one is unreachable. From a pinned link all its addresses are stored, as on the QR path: every later connection (API calls, uploads in the background session, unpairing) builds `ServerTrust` from the stored CA, which anchors that CA alone.
- **The typed code never leaves the phone on the link path.** The app fetches a nonce (`createPairingChallenge`) and sends `HMAC-SHA256(PBKDF2-HMAC-SHA256(code, "brievie-pair-v1" + pairing id, 600,000, 32), "brievie-pair-v1" + nonce + binding)` (`pairDeviceWithProof`). The binding is what TLS validated for that connection: the SHA-256 of the CA the app pinned (computed from the anchored certificate, not copied from the link), or, for a connection the system roots validated, the host name in A-label form. A host no public authority certifies (`.local`, `.lan`, `.home.arpa`, `.internal`, `.test`, single-label names, non-global IP addresses; `PairingProof.publicHostBinding`, a mirror of the host's `public_host_binding`) is not contacted on the link path without a pin; where the mirror could disagree with Python's `ipaddress` the app is stricter (IPv4-mapped, multicast, dotted numbers that are not plain IPv4). A relay named by a hostile link gets a proof for its own binding, which the real server refuses; guessing the code from it costs 600,000 PBKDF2 rounds per try. The QR path is unchanged and still sends the code to `pairDevice` (the QR comes from the server's own page).
- **The shared test vector** `Tests/Fixtures/pairing_proof_v1.json` is a verbatim copy of the host's `backend/tests/fixtures/pairing_proof_v1.json`; `PairingProofTests.theFixtureIsTheHostsFile` pins its SHA-256, so an edit on either side fails a test. It sits in the existing `Fixtures` resource folder (no `Package.swift` change).
- **PBKDF2 from CommonCrypto** (`CCKeyDerivationPBKDF`), HMAC from CryptoKit: system libraries, no package. The key is derived in a `@concurrent` function (off the main actor whatever the default isolation), only after a valid nonce arrived, into a byte buffer that is wiped with `memset_s` before the function returns; the HMAC key is CryptoKit's `SymmetricKey`, which zeroes its own storage. Only the proof leaves the function.
- **One refusal sentence.** A wrong proof, an unknown or used pairing (`pairing_code_invalid`) and an expired or replayed nonce (`pairing_challenge_invalid`) all map to `ServerError.invalidCode`; the sheet says "Deze koppelcode klopt niet of is verlopen. Typ de code opnieuw, of maak op de webpagina een nieuwe code." and clears the field. A server without the proof path (404 on the challenge, a 1c server) is `incompatibleServer`: never a fallback that sends the code.
- **Two new `BrievieServer` requirements** (`pairingChallenge`, `pairWithProof(at:trust:proof:deviceName:)`) with throwing defaults in a protocol extension, so the test conformers compile unchanged; `LiveBrievieServer` implements both. The proof's fields travel as one `CodeProof` value (SwiftLint's five-parameter limit). The nonce is accepted only as exactly 43 characters of the base64url alphabet (`A-Za-z0-9-_`, what the host's `secrets.token_urlsafe(32)` makes), checked by `PairingProof.isNonce` in the live client, in `PairingService` and inside `PairingProof` itself (it makes no proof for any other nonce). The proof's input `context + nonce + binding` has no length prefixes and is unambiguous only because the nonce's length is fixed: with a shorter nonce a hostile server could hand out a real nonce cut short and bind to a look-alike host that starts with the cut-off characters (`N[..<42]` + `"c" + "stijnvandepol.nl"` is the same input as `N` + `"stijnvandepol.nl"`), then relay the proof to the real server. Anything else is the `incompatible` refusal, and nothing is derived or sent.
- **Already paired: refuse with the way out** ("Tik dan in je werkruimtes op Ontkoppelen en open de link opnieuw."), never replace. **Locked: the link is dropped**, nothing shows above the lock and nothing is kept. While a pairing runs new links are ignored; a newer link replaces an open offer and clears the field.
- **Routing.** The `brievie` scheme has been registered since 1c (task links); `RootView.onOpenURL` sends only `brievie://server` links to `ServerLinkModel`, everything else keeps the no-op. The QR scanner sheet closes when the link sheet opens.
- **`AppVersionHeader`** owns `X-Brievie-App-Version` (`"<short> (<build>)"`): an API client middleware adds it to every request and the background upload request carries it; `pair` and `pairWithProof` also send it as `app_version` in the body. A value outside the server's accepted set (`^[0-9A-Za-z.+()\- ]{1,50}$`) is not sent at all. The CA download carries no header: it talks to a server nobody verified yet.
- **An expired token is a revoked token.** The host answers both with `401 not_authenticated`; the chain to the pairing screen was already there and is now pinned against the host's exact body. `session.revoked` names both causes: "Deze koppeling werkt niet meer: ze is ingetrokken of je hebt Brievie lang niet gebruikt. Koppel dit toestel opnieuw om verder te gaan."
- **Accepted risk: the offer survives backgrounding and the typed code is not cleared**, because the user switches to Safari to read the code; it is a one-time, ten-minute value that never leaves the phone. While the code field is on screen the privacy cover is up in the app switcher (`ServerLinkModel.asksForCode`); the rest of the unpaired app stays uncovered.
- **The notice's banner style comes from the model** (`Presentation.notice(_:kind:)`, warning for "already paired", error otherwise), not from comparing texts.
- **No new dependency.**

## Upright scans (2026-11-19)

- **Cause** (owner: "mijn brief stond er ineens gedraaid in"). The app does not lose the orientation: tests follow every EXIF orientation of a photo (macOS and simulator) and every `UIImage.Orientation` of a scanner page (simulator) through `prepare` and `jpeg` to the uploaded bytes, and each arrives as upright pixels without an orientation tag (`OrientationChainTests`). What is left is the document scanner itself: it crops and straightens, but "up" is the phone's up, and held flat above a letter on a table the phone does not know where the letter's top is. Not reproduced: the simulator has no camera, so this is the explanation that remains, not a proven one. A second defect came with it: Vision reads a turned page, but the app sorts lines by height, so a turned page's text went to the server in the wrong order.
- **Automatic upright from the text.** Apple's text recogniser (revision 3, the only one of the Swift API from iOS 18; its header says it improved rotated text) reads a page in any quarter turn and reports each line's corners. One reading of the page as it came in decides the turn (`PageOrientation`): each line votes for the turn that makes it read left to right, weighted by letters and digits times confidence; lines below 0.4 confidence do not vote; the page turns only when one direction has 80% of at least 12. Less text, or mixed directions, and the page stays as it is. An upright page costs nothing extra (the reading is the one that was already done); a turned page is turned and read once more, so the kept text is the upright page's in reading order. The JPEG holds upright pixels with no orientation tag, and the page hash is taken over those bytes, as before.
- **"Draai" before saving.** A scan no longer goes into the queue straight away: a screen ("Scan bewaren") shows each page as it will be uploaded (a 640-pixel JPEG of the same pixels) with "Draai" (a quarter clockwise; VoiceOver "Draai pagina 2") and, for a page the app turned, "De app heeft deze pagina rechtop gezet." A turn by hand is applied as it is (never corrected again) and the page is read again. "Bewaren" queues; "Annuleren" asks "Deze scan weggooien?" once there are pages and stops reading that still runs. The screen is pushed on the post's navigation stack, not a sheet, so it stays under the lock screen (as the reader). The pages as they came in stay in memory until saving or throwing away (compressed, at most 30), so a turn by hand encodes from the original and never from an earlier JPEG.
- **Performance.** Each page is decoded, turned, read and encoded off the main actor (`PageProcessor`, `@concurrent`), with a cancellation check between steps (this also closes the open item "page encoding runs on the main actor"). Measured on the generated A4 letters: macOS 26.6 (Apple silicon) 0.4 s for an upright page, 0.8 s for a turned one; iOS 26.4 simulator 1.2 to 1.5 s and 2.5 to 2.7 s (the simulator runs Vision on the Mac's CPU; a phone was not measured). A turn by hand on the simulator: 1.8 s.
- **One recognition at a time.** With many recognitions at once the test process crashed inside Vision (EXC_BAD_ACCESS while TextRecognition released a request, about one run in twelve). A process-wide queue (`RecognitionQueue`) lets one run at a time; the app reads one page at a time anyway. `make test` takes about 25 s longer for it.
- **Scan-quality set.** Twelve made-up letters (thirteen pages, texts in `Tests/BrievieScanTests/Fixtures/letters`) are drawn on A4, spoiled (skew up to 4°, blur, low contrast, shadow, speckles, four typefaces, JPEG), turned each quarter and run through `PageProcessor` with Vision: 52 pages, 224 facts (sender, letter date, amount, deadline phrase, addressee). The upright turn was found for all 52 pages on macOS, on the simulator and on GitHub's macOS runner. The set runs in `make test` and CI; `BRIEVIE_SKIP_VISION=1` leaves it out. Real letters stay out of the repository.
- **The set checks quality as a measured share, not per fact** (CI, PR #17). The first version expected every fact on every page, with a list of known losses per platform. Vision reads differently per machine: the CI runner lost facts that the Mac and the simulator kept (incasso in every turn, reclame) and kept some the Mac lost, so no list could gate CI. Now:
  - Hard on every page, everywhere: put upright, uploaded pixels portrait, text not empty, and the lines in the letter's order (the share of recognised lines that match the letter in order is at least 0.6; measured 0.83 to 1 for the upright pages, 0.19 to 0.36 for the same pages read turned without putting them upright).
  - Measured over the whole set: at least 88% of the 224 facts found, and no letter loses every fact in every turn. Observed with exact matching: macOS 95.5%, simulator 95.5%, CI runner 92.9% (16 lost); with the matching below: macOS 97.3% (four runs, the same), simulator 100%. The floor is a few points under the worst.
  - Matching (`FactMatcher`): case, accents and spacing never count. Amounts, dates and any phrase with a digit must be exact after that, so a misread number never passes. Names and phrases without digits also allow 1/l, 0/o, ignored punctuation and apostrophes, and one wrong, missing or extra character per ten ("'landerijn Incasso", "CZ. Zorgverzekcringen", "van de Po1" pass; another sender does not).
  - Every run prints one line with the share and one line per lost fact (letter, turn, fact, the line read instead), so a regression can be read from the CI log; `BRIEVIE_SCAN_REPORT=1` adds every page and the time per page.
  - What it no longer catches: the loss of a single fact on a single letter (a regression that costs a few facts stays above the floor), a name read with one wrong letter in ten, and lines dropped or merged by Vision (they do not count against the order).
- **Dropped:** reading each page at 0°, 90°, 180° and 270° and picking the best (revision 3 reads the same text in all four, measured: it does not tell the turns apart, and it costs four readings); `.fast` recognition for a probe (it found no text on these letters); trusting the scanner's page as upright (`PageSource.image` no longer claims so); a second automatic correction after a turn by hand.
- **Not verified on a device:** the scanner held flat (the cause above), the time per page on a phone, the push from the scanner's full-screen cover to the preview, VoiceOver on the preview (the labels are set; the screen was seen on the simulator with the largest text size, through a temporary demo that was not committed). iOS 18 reads with the same revision, but its models were not tested.

## Scheduled security audits (2026-11-19)

- **Three times a week.** `ci.yml` (03:41 UTC) and `codeql.yml` (05:17 UTC) also run on `main` every Monday, Wednesday and Friday, and on demand (`workflow_dispatch`); not on the hour, when many schedules start. On a schedule `ci.yml` runs only `secrets` (gitleaks over the full history); the macOS job `ci` judges the code and is skipped. CodeQL runs both languages. Concurrency groups contain the event name, so a scheduled run and a push run never cancel each other.
- **Issue on failure.** The job `audit-failed` (in both workflows, calling `.github/workflows/audit-failed.yml`, the same file as in `Brievie_host`) runs only on a failed scheduled run. It opens "Scheduled security audit failed" with the label `security-audit` (created if missing) or comments on the open one, with the run URL and the failed job ids and nothing else: no log lines, as a log can hold a finding that must be judged before it is public. `issues: write` on that job only; `gh` with the job token. The call uses `./` with a zizmor ignore, because zizmor 1.32 prefers `$/` and actionlint 1.7.12 rejects it.
- **CodeQL Swift on pull requests only when Swift changed.** The Swift analysis costs about 40 minutes, so a `changes` job (a diff against the pull request's base) decides: `*.swift`, `Package.resolved`, the Xcode project, `project.yml`, `*.xcconfig`, `Makefile`, `scripts/simulator-udid.sh`, the OpenAPI contract and its generator config, and the CodeQL workflow itself count. Other events always run it. Chosen: the matrix job `Analyze (swift)` is always there and, when nothing changed, takes a Linux runner and says "Skipped: no Swift change" in its log and summary. Dropped: `paths` filters on the workflow, because a required check that is never reported blocks merging (the ruleset requires `ci` and `secrets` today, not `Analyze (swift)`, but it may later). The `actions` leg and a skipped Swift leg now run on Linux; only the Swift build needs macOS.
- **Dropped:** daily runs (a few days of delay is fine for this app, which has no server-side exposure of its own, and the macOS minutes cost); an external monitoring service (an account and a third party for what GitHub already shows). Limit: GitHub switches off scheduled workflows of a public repository after 60 days without repository activity; enable them again in the Actions tab after a long pause.

## Deadline reminders (2026-11-19)

The owner wants notifications on the phone. First step, agreed: reminders the app makes itself; nothing leaves the server, no external service.

- **Local notifications (`UserNotifications`), no push.** The app plans them from the open tasks it read and hands them to the system, which shows them at the moment set, also when the app is not running. No entitlement and no Info.plist key: local notifications need neither (`aps-environment` is for push only); the project, the entitlements and the bundle ids are unchanged. No new dependency.
- **Off until the user turns it on:** "Meldingen voor termijnen" in the settings (section "Meldingen", one switch for this phone, not per workspace). Turning it on asks the system at that moment (only when it never asked); a refusal turns it back off with "Brievie mag geen meldingen sturen. Zet meldingen voor Brievie aan in Instellingen." and "Open Instellingen". Notifications switched off later in Settings: the switch stays on and says so, and reminders come again once they are allowed.
- **Rules** (`ReminderPlanner`, pure, with clock and time zone injected): for every open task with a deadline in the workspaces this phone is paired to, one reminder some days before and one on the day, both at 09:00. The lead time is a setting, "Eerste melding": on the day only, 1, 2 or 3 days (default) or a week before. Nothing for a done task, a task without deadline, a deadline in the past, or a moment that has passed (the day itself after nine gets nothing). A first notice whose day has already passed while the deadline is still ahead becomes one catch-up at the next 09:00 (today before nine, else tomorrow) with the right "morgen" / "over N dagen", never on the deadline itself (that day has its own, so one task never rings twice on a day). Catch-ups are remembered (`reminders.catchUps`, with the deadline they were made for), so one that went off is not made again the next day, also in a new process; a moved deadline starts afresh, and a catch-up the 64 limit left out is not remembered. The trigger is a calendar date and time without a time zone, so it rings at 09:00 wherever the phone is then, also across summer time (tests: midnight in Amsterdam and Los Angeles, both changes of summer time).
- **What the lock screen shows.** By default only "Een termijn loopt over 3 dagen af." / "morgen af." / "vandaag af.": nothing from the letter. "Toon de afzender in meldingen" (off by default) makes it "Een termijn van <afzender> loopt …" (one line, cut at 40 characters); an amount or the task's description never appears. No title: the system shows the app's name above every notification, so "Brievie:" in the text would say it twice. The notification carries the workspace and letter ids only (never shown). A tap opens the app behind its lock, as always; once unlocked it shows that workspace (closing the settings) and pushes the letter; a workspace the phone no longer has, or a task without a letter, just opens the app.
- **iOS keeps at most 64 pending local notifications per app.** The nearest 64 are scheduled (32 tasks at two reminders each); the rest are planned at a later refresh, once the nearest have gone off. Reminders kept for a workspace that could not be read count towards the 64.
- **When they follow the tasks:** every workspaces load (opening the app, every unlock, the settings, pull-to-refresh), after a confirm or a ticked task, and after a changed setting. Each refresh reads the open tasks again: a completed task or a moved deadline changes its reminders (same identifier `deadline.<workspace>.<task>.<ahead|day>`, so a new date replaces the old one), a workspace that is no longer listed loses its reminders, a reminder already shown for a task that is done leaves Notification Centre. A workspace whose tasks cannot be read keeps its reminders (an unreachable server does not mean the deadlines are gone). Before the first workspaces load of a process nothing is changed (the reminders of the last run stay). Switching off removes every pending and shown reminder at once; so does forgetting the pairing ("Ontkoppelen" and a revocation, in `AppModel.clearForgottenPairing`), which also turns the switch off. Calls run one at a time in order, so a removal asked for during a refresh wins.
- **The honest limit.** Reminders only know what the app last read. The app has no background refresh (its only background work is the background `URLSession` for uploads; no `UIBackgroundModes`), so a deadline confirmed in the web gets its reminders the next time the app opens, and a task done in the web keeps its reminders until then. The footer says: "Brievie herinnert je aan termijnen die de app kent. Open de app af en toe, dan blijft dat bij."
- **`UserDefaults`: the fourth sanctioned use**, the reminder settings (`reminders.enabled`, `reminders.leadDays`, `reminders.showsSender`, `reminders.catchUps`; none a secret), behind `ReminderSettings`, covered by the privacy manifest's `CA92.1`; forgotten with the pairing.
- **Dropped:** server push (APNs needs a service on the server side, Apple's push channel and a device token on the server: data would leave the home server, which this first step rules out); a background fetch (`BGAppRefreshTask`: iOS decides when and whether it runs, and every run would contact the server from the background; not now); a switch per workspace (one per phone is simpler, and the text names no workspace); time-sensitive notifications (need an entitlement).
- **Not verified on a device.** Seen in the simulator (temporary demo, not committed): the switch, the system's question, "Eerste melding" and the sender switch, four reminders handed to the system. Not seen: a reminder going off on the lock screen, a tap on it opening the letter, "Open Instellingen" after a refusal, VoiceOver.
- **Calendar and notifications both on** (coordinator decision): no change; while a calendar switch is on the footer adds "Staat 'Zet termijnen in mijn agenda' ook aan? Dan meldt de agenda de termijnen ook." (the calendar's alarms ring 7 and 2 days before and on the day, so "twee meldingen" would not be exact).
